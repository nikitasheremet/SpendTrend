# SPE-117: Add filtering to the generic table

## Problem

`GenericTable.vue` (`src/components/DesignSystem/Table/`) has no filtering,
sorting, or search today — `data` is rendered as-is (only sliced for
progressive/virtualized rendering). The `Table/README.md` explicitly lists
"Sorting and filtering support" as a future enhancement. This ticket adds
**filtering only**, scoped to `dropdown` and `date` typed columns, with an
architecture that leaves room for **sort** and **search** to be added later
(separate tickets) without reshaping the table again.

---

## Design decision 1: filter bar vs. per-column header dropdown

| | Filter bar (toolbar above table) | Column header dropdown (Excel/Sheets-style) |
|---|---|---|
| **UX discoverability** | Filters are always visible as a group — easy to scan "what's currently filtered" at a glance | Filters are hidden until a filter icon is clicked; discoverable via familiar spreadsheet convention |
| **UX scaling** | Gets cramped with many filterable columns or long labels; needs wrapping/scrolling on narrow screens | Scales naturally — filter icon lives in the header cell that already has space for the column label |
| **Spatial relationship** | Filter control is separated from the column it filters (extra visual mapping step) | Filter control sits directly next to the data it filters — matches user's mental model |
| **Combine with future sort** | Sort arrows would need their own separate spot in the header row, disconnected from the filter bar | Sort control (arrow) and filter control (icon) can live in the same header cell — one coherent "column controls" area |
| **Combine with future search** | A global search box fits naturally in the same toolbar | Search is orthogonal either way (global, not per-column); no advantage either direction |
| **Code: new UI needed** | One new toolbar component + one control per filterable column type | One small filter-icon trigger per filterable header cell + one floating panel component (dropdown checklist / date range), reusing existing positioning primitives |
| **Code: reuse in this repo** | No existing "toolbar" pattern to build on | `DropdownWithInput.vue` + `DropdownOptions.vue` + `useDropdownPosition` already implement a floating, teleported, position-aware panel anchored to a trigger — the filter panel is a structural sibling of this, not a new pattern |
| **Code: state shape** | Same either way — a `Record<columnKey, FilterValue>` | Same either way |

**Decision: column header dropdown (Excel/Sheets-style).**

Reasoning: this repo already has the exact reusable primitive needed
(`useDropdownPosition` + a teleported floating panel, as used by
`DropdownWithInput`/`DropdownOptions`), so the header-dropdown approach is
*not* more code than a filter bar here — it's less, because there's no new
toolbar layout to design. It also composes more naturally with the future
sort feature (arrow + filter icon can share the same header cell control
area) per the ticket's explicit ask to plan for that. A filter bar remains a
reasonable alternative and is called out here in case reviewers weigh the
discoverability tradeoff differently. This decision was reviewed and
approved before implementation steps below were started.

---

## Design decision 2: who resolves filter options?

**Decision: the generic table resolves options itself — no separate
`filterOptions` prop.**

- For `dropdown` columns: derive the option list from the **distinct values
  actually present in `data`** for that column key (sorted), not from
  `column.dropdownOptions`. `dropdownOptions` describes what's *editable*
  into a cell (including options that may not appear in any row yet);
  filtering should only ever offer values a user could actually match,
  which is exactly what Excel/Sheets does. This also means filtering works
  even on `dropdown` columns that don't define `dropdownOptions` at all.
- For `date` columns: there's no fixed option list (high cardinality) — the
  panel is a `from`/`to` date range, not a checklist. No option resolution
  needed; the table just needs the raw date value already in `data`.
- This avoids the data-duplication problem called out in the ticket (no
  second source of truth for "what are the valid filter values"), matches
  the ticket author's stated leaning, and requires zero new props on
  `ColumnConfig` beyond a single `filterable` boolean.

---

## Design decision 3: extensibility for future sort & search

- Filtering will be implemented as a standalone composable
  (`useTableFilters`) that takes `data` + `columns` and returns **rows
  paired with their original index** (`{ row: T; index: number }[]`), not
  a plain filtered array. `GenericTable.vue` renders from these pairs
  using the **original index**, not the position in the filtered list.
  This matters because `rowActions`, `validationErrors` (a `Set<number>`),
  and the `cell:changed` emit are all index-addressed against the full
  `props.data` array — losing the original index on filter would silently
  break edits/validation-highlighting/row actions on any consumer that
  keys off `rowIndex` (e.g. `useTableOperations.updateCell`,
  `ExpenseDataTable`/`AddExpenseTable`/`IncomeDataTable` stores). This is
  the main correctness risk in this feature and needs explicit test
  coverage.
- Future `useTableSearch` / `useTableSort` composables are expected to
  follow the same `{ row, index }[]` in/out shape, so they can be composed
  in a pipeline (`search → filter → sort`) without `GenericTable.vue`
  needing to know about all three at once. Document this expectation in
  `Table/README.md` so the next ticket doesn't reinvent the shape.
- `ColumnConfig.filterable` is intentionally a separate flag from `type`,
  so a future ticket can add `filterable` support for `text`/`number`
  columns later just by extending `useTableFilters`, without touching
  `GenericTable.vue`'s rendering/index-mapping logic again.

## Implementation steps

### 1. `types.ts` — new types

- [x] Add `filterable?: boolean` to `ColumnConfig<T>`, next to `editable`.
- [x] Add:
  ```ts
  export interface DateFilterValue {
    from?: string
    to?: string
  }
  export type FilterValue = string[] | DateFilterValue
  export type FilterState = Record<string, FilterValue>
  ```
- [x] Note in a code comment that `filterable` is only honored for
      `type: 'dropdown' | 'date'` columns (text/number filtering is out of
      scope — future ticket).

### 2. `hooks/useTableFilters.ts` — new composable

- [x] Accept `data: ComputedRef<T[]>` and `columns: ComputedRef<ColumnConfig<T>[]>`.
- [x] Internal `activeFilters = ref<FilterState>({})`.
- [x] `filterableColumns = computed(...)` — columns where
      `filterable === true` and `type` is `'dropdown'` or `'date'`.
- [x] `getDropdownOptions(column): string[]` — map `data.value` to
      `String(row[column.key])`, dedupe, drop empty/undefined, sort.
- [x] `filteredEntries = computed(() => data.value.map((row, index) => ({row, index})).filter(...))`
      — a row passes if it matches every active filter:
      - dropdown filter (string[]): row passes if `activeFilters[key]` is
        empty OR `String(row[key])` is in the array (empty selection =
        no filtering, not "filter out everything" — matches Excel).
      - date filter (`{from?, to?}`): row passes if `from`/`to` unset or
        the row's date value falls within the (inclusive) bounds.
- [x] `setFilter(key, value)`, `clearFilter(key)`, `clearAllFilters()`.
- [x] `isColumnFiltered(key): boolean` — for the header active-indicator.
- [x] Return all of the above plus `filterableColumns`, `getDropdownOptions`.

### 3. `hooks/index.ts`

- [x] Export `useTableFilters` alongside the existing `useProgressiveRowRender` export.

## What is NOT changing / out of scope

- No text or number column filtering (future ticket).
- No sort or search implementation (future tickets) — only the
  `{row,index}` composable shape is established to make those additive.
- No changes to `useTableOperations` — it remains index-addressed against
  the full `rows` array, which continues to work because `GenericTable`
  always passes original indices through, filtered or not.
- No changes to `TableCell.vue`/`TableRow.vue` beyond what's implied by
  `GenericTable` passing `row`/`row-index` from `{row,index}` pairs instead
  of a plain loop index (their prop contracts are unchanged).
- `IncomeDataTable` and `AddIncomeTable` are not touched in this ticket;
  `ExpenseDataTable` and `AddExpenseTable` are updated as proof-of-concept
  example consumers (date + category + subCategory filters).

## Edge cases

| Scenario | Expected behaviour |
|---|---|
| Column has `type: 'dropdown'` but no rows have a value for it | `getDropdownOptions` returns `[]`; filter icon still renders but the panel shows no options (or an empty-state message) |
| All rows filtered out | Table renders an empty `<tbody>`; no crash in `useProgressiveRowRender` on a zero-length input |
| `data` changes (e.g. a row added) while a filter is active | `filteredEntries` recomputes reactively; newly-added rows are included/excluded per the active filter automatically |
| A filtered-out row is the one being edited elsewhere (e.g. via `rowActions`) | Not reachable through the UI once filtered out; no special handling needed since actions are only wired to rendered rows |
| Date column has invalid/unparseable date string in a row | Row is excluded from range matching rather than throwing; treat as "doesn't match" |
| Column marked `filterable: true` with `type` unset (defaults implied) | No filter icon renders — `filterable` only applies to `dropdown`/`date` per Design decision 3 |
