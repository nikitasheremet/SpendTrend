# SPE-120: Add search to the generic table

## Problem

`GenericTable.vue` (`src/components/DesignSystem/Table/`) already supports
per-column **filtering** (dropdown / date) via the `useTableFilters` hook and a
sticky `TableHeaders` row. This ticket adds a **free-text search bar** directly
above the table headers:

- A small search input, **stickied** the same way the headers are.
- Columns gain a new `searchable?: boolean` prop.
- Typing text filters rows down to those where the search term is contained
  (case-insensitive `includes`) in **any** column marked `searchable`.
- Search must combine with the existing column filters (both must pass).

The ticket explicitly asks whether the existing filtering logic can be
**re-used / expanded**. It can — see the design decision below.

---

## Design decision: extend `useTableFilters` vs. a separate search hook

The existing filtering pipeline lives entirely in
`hooks/useTableFilters.ts`. Its `filteredEntries` computed already:

- maps `data` to `{ row, index }` entries (preserving **original** indices,
  which downstream code — `cell:changed`, row actions, `validationErrors` —
  depends on),
- filters by "row passes **every** filterable column".

Search is conceptually the same operation: another predicate a row must satisfy
to remain visible. Adding a second parallel hook/pipeline would mean two
`computed` passes over the data and two places that must agree on the
index-preserving entry shape.

**Decision: expand `useTableFilters` to also own search state and matching.**

- Add `searchTerm` state + `setSearchTerm` to the hook.
- Add a `searchableColumns` computed (columns with `searchable === true`).
- Extend the single `filteredEntries` computed so a row is kept only if it
  passes **both** the column filters (existing behaviour) **and** the search
  predicate (new). Search with an empty/whitespace term is a no-op (keeps all).
- The UI (search bar) stays a separate presentational component; only the
  matching logic and state are centralised in the hook.

This keeps one filtering pass, one entry shape, and one source of truth for
"which rows are visible", which is exactly the re-use the ticket asks for.

### Search matching semantics
- Case-insensitive `String(rawValue).toLowerCase().includes(term.toLowerCase())`.
- Read the raw cell value with the hook's existing `getRawValue(row, key)`
  helper (so behaviour matches the filters). For columns whose displayed value
  comes from `calculate`, apply `column.calculate(row)` when present before
  stringifying, so what the user sees is what they search (mirror the value
  resolution `TableCell.vue` uses).
- Empty / whitespace-only search term ⇒ every row matches (no filtering).
- A row matches if **any** searchable column contains the term.
- `null` / `undefined` / `''` cell values never match a non-empty term.

## Implementation checklist

### 1. Types (`types.ts`)
- [x] Add `searchable?: boolean` to `ColumnConfig<T>`.
- [x] (No new filter-type constants needed — search is type-agnostic, works on
      any column regardless of `type`.)

### 2. Extend the filtering hook (`hooks/useTableFilters.ts`)
- [x] Add `searchTerm: Ref<string>` internal state (default `''`).
- [x] Add `searchableColumns` computed: `columns.value.filter(c => c.searchable === true)`.
- [x] Add helper `getSearchableValue(row, column)`: use `column.calculate(row)`
      when defined, else `getRawValue(row, column.key)`; return the stringified
      value (or `''` for empty values).
- [x] Add `rowMatchesSearch(row)`: return `true` when `searchTerm` is empty
      after trim; otherwise `true` iff some `searchableColumns` value contains
      the lowercased term.
- [x] Update `filteredEntries` to keep entries where
      `filterableColumns.every(columnMatches)` **and** `rowMatchesSearch(row)`.
- [x] Add `setSearchTerm(value: string)` setter.
- [x] Export `searchTerm`, `searchableColumns`, `setSearchTerm` from the hook
      return + update `UseTableFiltersReturn<T>` interface.
- [x] Keep `hooks/index.ts` re-exports valid (interface changes only, no new
      export file needed).

### 3. Search bar component (`Table/TableSearchBar.vue`)
- [x] New presentational component: a single text `Input` (reuse
      `DesignSystem/Input.vue`, as `TableColumnFilter` does) with a placeholder
      like `Search…` and an appropriate `aria-label` (e.g. `Search table`).
- [x] Props: `modelValue: string`, `stickyTopOffsetPx?: number`.
      Emit `update:modelValue` (use `defineModel`).
- [x] Wrap in a `<div>` that is `sticky` at `top: stickyTopOffsetPx` with a
      white/opaque background and a sensible `z-index` (reuse the same
      `z-table-header` token used by headers so it layers above body rows), so
      it pins under the nav exactly like the header row does.
- [x] Keep it compact ("small search bar") — constrain width, not full-bleed.

### 4. Sticky layout wiring (`GenericTable.vue` + `TableHeaders.vue`)
- [x] In `GenericTable.vue`, render `<TableSearchBar>` **above** the `<table>`,
      only when `searchableColumns.value.length > 0`.
- [x] Bind its `model-value`/`update:model-value` to the hook's `searchTerm` /
      `setSearchTerm`.
- [x] Sticky stacking: the search bar pins at `stickyTopOffsetPx` (falling back
      to the `nav` spacing token, matching `TableHeaders`' current default).
      The header row must then pin **below** the search bar. Measure the search
      bar height with the existing `useElementHeight` hook
      (`helpers/hooks/useElementHeight.ts`) and pass
      `stickyTopOffsetPx + searchBarHeight` as the `sticky-top-offset-px` prop
      to `TableHeaders`, so headers stay flush under the search bar and never
      overlap it. (When no searchable columns, pass the original offset.)
- [x] Resolve the base offset default (`stickyTopOffsetPx ?? getThemeSpacingPx('nav')`)
      once in `GenericTable` so both the search bar and the header offset use the
      same base; `TableHeaders` already applies the same fallback for the case it
      is used standalone.
- [x] No change needed to `TableHeaders` internals — it already accepts and
      applies `stickyTopOffsetPx`.

### 5. Re-render / interaction
- [x] Confirm `filteredEntries` feeds `useProgressiveRowRender` (unchanged) so
      search results respect progressive rendering and original indices — no
      change to `getRowKey`, `cell:changed`, row actions, or `validationErrors`
      wiring is required (they key off `entry.index`).

## Out of scope / notes
- Exact-`contains` matching only (per ticket "match the text exactly … via
  contains"). No fuzzy / token / regex search.
- No debounce is strictly required for correctness; matching is cheap and runs
  through the same computed. If large datasets prove janky, a debounced
  `searchTerm` (reuse `helpers/hooks/useDebounce.ts`) can be layered in later —
  called out but not implemented here to keep the change minimal.
- Search is global across searchable columns, not per-column — consistent with
  the ticket description.
