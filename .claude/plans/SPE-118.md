# SPE-118: Add sort to generic table

Linear: https://linear.app/spendtrend/issue/SPE-118/add-sort-to-generic-table

## Context from codebase exploration

- Table lives at `packages/frontend/src/components/DesignSystem/Table/` (Vue 3 `<script setup>` + TS, Vitest + `@vue/test-utils`, no Jest/RTL).
- `GenericTable.vue` composes `useTableFilters` → `filteredEntries: { row: T; index: number }[]` → `useProgressiveRowRender` → `visibleData` rendered in the `<tbody>`. Header markup is a separate component, `TableHeaders.vue`, driven by a `headers: TableHeader[]` computed built in `GenericTable.vue:73-94`.
- Filtering already establishes the pattern to follow: a `ColumnConfig` flag (`filterable`), a `TableHeader` sub-shape (`filterKey`/`filterType`/`filterOptions`/`filterValue`), a small trigger button embedded per-`<th>` in `TableHeaders.vue`, an event bubbled up (`filter:changed`) and handled in `GenericTable.vue` (`handleFilterChange` → `setFilter`), and a composable (`useTableFilters`) owning all filter state and exposing `{ row, index }[]` in/out.
- `README.md` (lines 279-284, 409) explicitly documents the intended contract: future `useTableSort` should consume/produce the same `{ row, index }[]` shape as `useTableFilters` so it can be chained `search → filter → sort` without `GenericTable.vue` special-casing each concern. We must honor this.
- No existing sort code anywhere in the table directory — this is greenfield.

## UX recommendation

Put the sort control **in the header cell next to the filter button**, as a separate small clickable affordance — not merged into the filter dropdown modal, and not merged into the filter trigger button itself.

Reasoning:
- Filtering and sorting are different mental operations (narrowing rows vs. reordering rows) and Excel/Sheets — which this table already models itself after (per README) — keeps them as visually distinct controls in the header, even though both live in the same corner of the cell. Users scan for them independently.
- Sort needs to show *current state* at a glance (unsorted / asc / desc) via an always-visible glyph, whereas the filter button only needs to indicate active/inactive. Collapsing sort into the filter dropdown would hide sort state behind a click, which fails the "which column is sorted" glanceability the ticket cares about.
- It reuses the exact interaction pattern already proven for the filter button (small `w-5 h-5` icon button, `aria-label`, sits inline in the `<span class="inline-flex items-center gap-1">` header wrapper) — cheapest to build, most consistent to use, no new modal/popover machinery needed for the MVP.
- Concretely: add a sort button (▲/▼/⇅ glyph, same visual weight as the ▼ filter glyph) right after the label and before/after the filter button in `TableHeaders.vue`'s header `<span>`. Click cycles the column's state; only one glyph state is shown per column at a time.

## Implementation plan

### 1. Types (`types.ts`)
- [ ] Add `export type SortDirection = 'asc' | 'desc'`. "Unsorted" is represented as `undefined` (never `null`) — mirrors how `activeFilters` uses absence-of-key for "no filter." Applies everywhere a direction can be missing: `getSortDirection(key): SortDirection | undefined`, `TableHeader.sortDirection?: SortDirection`, etc.
- [ ] Add `sortable?: boolean` to `ColumnConfig<T>`.
- [ ] Add a `SortState` type shaped for **future multi-column support without over-building now**: `export interface SortRule { key: string; direction: SortDirection }` and `export type SortState = SortRule[]`. For this ticket the array will only ever hold 0 or 1 entries (enforced by the composable, not the type), but keeping it as an array means a future multi-column ticket only changes the composable's internals, not the type contract or `GenericTable.vue`'s wiring.
- [ ] Extend `TableHeader` with `sortable?: boolean`, `sortKey?: string`, `sortDirection?: SortDirection` (mirrors the `filterable`/`filterKey`/`filterType`/`filterValue` quartet already there).

### 2. `useTableSort` composable (`hooks/useTableSort.ts`)
- [ ] Model directly on `useTableFilters.ts`. Signature:
  ```ts
  interface UseTableSortOptions<T> {
    columns: ComputedRef<ColumnConfig<T>[]>
  }
  interface UseTableSortReturn<T> {
    sortableColumns: ComputedRef<ColumnConfig<T>[]>
    sortState: Ref<SortState>            // array of 0-1 SortRule for now
    sortedEntries: (entries: TableFilterEntry<T>[]) => TableFilterEntry<T>[]
    toggleSort: (key: string) => void     // cycles unsorted -> asc -> desc -> unsorted
    getSortDirection: (key: string) => SortDirection | undefined
  }
  ```
- [ ] `sortedEntries` takes `TableFilterEntry<T>[]` (the same `{ row, index }[]` shape `useTableFilters.filteredEntries` produces) and returns the same shape, sorted — this is the composability contract the README calls for. Internally: if `sortState.value` is empty, return input unchanged (identity, no copy needed beyond what callers expect); otherwise sort a shallow copy by comparing `getRawValue(row, rule.key)` for each rule in order (only one rule exists today, but looping the array means multi-column later is just "stop clamping the array length").
- [ ] Comparator: reuse/extract a `getRawValue` helper (currently duplicated inline in `useTableFilters.ts:36-38`) — either import it from a shared location or duplicate it locally with a short comment; decide during implementation which is less churn. Handle `undefined`/`null` (sort to end regardless of direction — stable, predictable), numbers via numeric compare, strings via `localeCompare`, dates (ISO strings) via `Date` parse compare — mirror the type-driven branching style of `matchesDropdownFilter`/`matchesDateFilter`.
- [ ] `toggleSort(key)` enforces the single-column constraint **at this layer**: setting a new key's state always replaces `sortState.value` wholesale (`[{ key, direction }]` or `[]`), never appends. This is the one place the "only one column at a time" rule lives, so relaxing it later (to append instead of replace) is a one-function change.
  - Cycle order per ticket: click on unsorted column → asc; click again (same column, currently asc) → desc; click again (same column, currently desc) → unsorted (`[]`); clicking a *different* column while one is active jumps straight to that column's asc state (replacing the old rule), matching "sort from the first column will be removed, and sort applied to the next."
- [ ] `sortableColumns` mirrors `filterableColumns`: `columns.value.filter(col => col.sortable === true)`.
- [ ] `getSortDirection(key)` returns the direction if `key` is the (only) entry in `sortState.value`, else `undefined` — used to drive header glyph state.

### 3. Wire into `GenericTable.vue`
- [ ] Import `useTableSort` from `./hooks`, call it with `columns: computed(() => columns)`.
- [ ] Chain: `filteredEntries` (from `useTableFilters`) → `sortedEntries(filteredEntries.value)` (wrap in a `computed`) → feed that computed into `useProgressiveRowRender`'s `data` option instead of `filteredEntries` directly. This keeps `filter → sort → progressive render` as the pipeline order, consistent with the README's `search → filter → sort` contract (search doesn't exist yet, so pipeline starts at filter).
- [ ] Extend the `headers` computed (lines 73-94) to also set `sortable`, `sortKey`, `sortDirection` per column, analogous to how `filterable`/`filterKey`/etc. are set today.
- [ ] Add `handleSortChange(key: string)` calling `toggleSort(key)`, wired to a new `@sort:changed` (or similar) event emitted from `TableHeaders.vue`.

### 4. `TableHeaders.vue`
- [ ] Add `'sort:changed': [key: string]` to `defineEmits`.
- [ ] Add a small sort trigger button in the header `<span>`, following the same structural pattern as the existing `TableColumnFilter` button (`aria-label="Sort by {label}"`, `aria-pressed`/`aria-sort` semantics — consider using the native `aria-sort="ascending"|"descending"|"none"` attribute on the `<th>` itself for accessibility, since that's the standard table-sort ARIA pattern and costs nothing extra).
- [ ] Glyph should reflect current 3-state value, using plain line arrows (not filled triangles) so the sort control reads as visually distinct from the filter button's `▼` (U+25BC BLACK DOWN-POINTING TRIANGLE):
  - unsorted → `↕` (U+2195 UP DOWN ARROW), muted/low-opacity to signal inactive
  - asc → `↑` (U+2191 UPWARDS ARROW)
  - desc → `↓` (U+2193 DOWNWARDS ARROW)
  Follow the same "small `w-5 h-5` button, `text-blue-600` when active / `text-gray-500` when not" visual treatment as the filter button for consistency in sizing/spacing, while the glyph shape itself keeps the two controls from being confused at a glance.
- [ ] `v-if="header.sortable && header.sortKey"` guard, matching the filter button's `v-if` style.

### 5. `hooks/index.ts`
- [ ] Export `useTableSort` (and its types if other files import them, matching how `useTableFilters` is exported).

### 6. Unit tests
- [ ] `hooks/__tests__/useTableSort.test.ts` — mirror `useTableFilters.test.ts`'s `describe('when ...', () => { it('should ...') })` style. Cover:
  - unsorted → asc → desc → unsorted cycle via repeated `toggleSort(sameKey)` calls, asserting `getSortDirection`/`sortState` after each call.
  - clicking a different column while one is sorted replaces the sort state entirely (old key's `getSortDirection` becomes `undefined`, new key starts at `asc`), never accumulates multiple rules.
  - `sortedEntries` sorts strings, numbers, dates correctly in both directions (one case per `CellType` that's sortable).
  - `sortedEntries` with empty `sortState` returns entries unchanged/in original order.
  - rows with `undefined`/`null`/empty values sort to the end regardless of direction.
  - `sortedEntries` preserves the `{ row, index }` shape and the original `index` values (index must still map back to the unfiltered `data` array, same invariant `useTableFilters` has to preserve for `validationErrors`/`cell:changed`).
  - `sortableColumns` only includes columns with `sortable: true`.
- [ ] `__tests__/GenericTable.test.ts` — add a new `describe('when columns are sortable', ...)` block (sibling to the existing `'when columns are filterable'` block, same helper/query patterns — find the sort button via `aria-label`, click it, assert row order via `TableRowComponent` props):
  - clicking sort on a sortable column reorders rendered rows asc, then desc, then back to original order on the third click.
  - clicking sort on column A then column B: column A's row order effect is undone and column B's applied (verifies single-column-at-a-time end-to-end, not just at the hook level).
  - sort composes correctly with an active filter (filter first, then sort within the filtered subset) — add a case combining both `TableColumnFilter` interaction and the new sort button in one test.
  - non-`sortable` columns render without a sort button (guard against accidentally showing it for all columns).
- [ ] Run `npm run test:unit` (per README's Testing section) scoped to the Table directory/affected files and confirm all pass, including pre-existing filter/row/cell tests (regression check on the pipeline change in `GenericTable.vue`).

### 7. Documentation
- [ ] Update `Table/README.md`: add a `## Sorting` section (mirroring `## Filtering`'s structure) documenting the 3-state cycle, single-column constraint, `sortable` column config flag, and the `{ row, index }[]` pipeline shape now realized (not just promised). Remove "Sorting" from `## Future Enhancements` since it's now implemented; leave "search" there since it's still unbuilt.

## Explicitly out of scope for this ticket
- Multi-column sort UI/interaction (shift-click, sort priority badges, etc.) — only the data structures (`SortState` as an array, `sortedEntries` looping over rules) are shaped to make this a future additive change.
- A sort-selection modal alongside the filter dropdown — rejected in favor of the inline header button per the UX recommendation above.
- Search composable — out of scope, only mentioned because it shares the same pipeline contract.
